# workstation second archive copy (D3)

Approved design, installed through its gate on 2026-09-30. The source
is the NAS-mounted `/mnt/pve/synology-backup/dump` on one Proxmox node; the
destination is `D:\homelab-backups` on workstation. Both copies remain on-site
and desktop ransomware can damage D:. Nothing deletes or prunes a copy.

## Node selection and prerequisites

Confirmed node: `pve1` / pve1, `192.168.0.11`. Recorded 2026-09-19 evidence
gives it about 7.6 GiB uncommitted RAM, 12 CPU threads and NVMe; the smaller
nodes have less headroom. The 2026-09-30 23:14 PDT gated preflight then measured
its five-minute load per CPU as 0.02779 and confirmed it was least loaded among
the three nodes mounting the backup share. Host identity and public pins passed.
The operator entered the root password only in their terminal because the
existing admin public key was rejected. The stage recap was `ok=7 changed=2
unreachable=0 failed=0`: server and one restricted key installed on pve1 only.

Before any mutation, the stage compares each node's five-minute CPU load
divided by CPU count, considers only nodes mounting synology-backup, and
requires the confirmed node to be least loaded. If a different node wins,
it stops before installing anything; review that node's exact confirmation.
The stage installs one key only on one node, never a key on all three.

Other prerequisites: normal admin SSH authorization and verified host pins
for the three inventory nodes; finalized vzdump archives; healthy NAS mount;
D: present and at least 100 GB free plus the selected archives' sizes;
Windows OpenSSH client; interactive operator login; a dedicated public key.
The SSH key must be generated by the operator (private half never near chat):

```powershell
ssh-keygen -t ed25519 -f "$HOME/.ssh/homelab_backup_pull_ed25519" -C homelab-backup-pull
```

Press Enter at both passphrase prompts. This avoids PowerShell dropping an
empty `-N` argument and causing `Too many arguments`. Do not overwrite an
existing key. This key has **no passphrase** so the task
can run without a credential prompt. Its forced command and source restriction
limit it to reading archives from `192.168.0.70`. Only the `.pub` is supplied
to the agent; the agent never generates, reads or copies the private key.

## The Proxmox gate

Stage: `make -C platform/proxmox configure-backup-pull`.
Defaults: `allow_backup_pull=false`, `backup_pull_confirmation=""`.
The operator supplied the exact pve1 confirmation on 2026-09-30. It is
accepted for this stage only. The operator generated the dedicated key and
the agent verified only its public half on 2026-09-30. All three public host
fingerprints match `inventory/lab.yml`. Admin key authentication is rejected;
root password authentication must happen only in the operator's terminal.
The single-node stage succeeded. The Windows task was registered and its first
run started at 23:18 PDT. Task registration is not archive acceptance: require
the hash/source checks below and a successful completed run.
The exact candidate confirmation is:

```text
INSTALL BACKUP PULL ON pve1 192.168.0.11
```

After the operator supplies it, use one ephemeral `EXTRA_JSON` object with
`allow_backup_pull`, `backup_pull_confirmation`, `backup_pull_node` and
`backup_pull_public_key`. Never store an approval in defaults or a file.
The agent may run this single stage only after the exact operator approval.
The play is serial/fatal and checks the host identity and mount before changes.
If only root password login works, run the same single Make stage interactively
in the devcontainer with Ansible's `--ask-pass`, verified public host pins and
per-invocation SSH arguments enabling that password prompt. Do not put a
password in arguments, environment variables, files, logs or chat. Do not
change the persistent key-only Ansible configuration or install another admin
key as a substitute for this stage. The prompt uses one password for the three
inventory nodes; if it fails on any node, stop before mutation and resolve the
operator's authentication path.

The installed authorized-key options are exactly:

```text
from="192.168.0.70",command="/usr/local/sbin/homelab-backup-pull",no-port-forwarding,no-agent-forwarding,no-pty,no-X11-forwarding
```

The server only accepts `list` or `get <strict finalized archive name>`.
`list` returns tab-separated name, size and SHA-256; `get` streams bytes.
It opens only regular files without following symlinks, using read-only
descriptors relative to the fixed dump directory. It detects changes while
reading and never writes, renames, removes or executes archive content.

## Verified host pin and Windows task

Export public node identity from the canonical inventory in the devcontainer:

```bash
python3 platform/proxmox/scripts/backup_pull_config.py --node pve1
```

Save that JSON as `D:\homelab-backups\backup-node.json` (not a secret).
Obtain the node's **public** ED25519 host-key line into an operator-chosen
temporary file, for example with `ssh-keyscan -t ed25519 192.168.0.11`.
Keyscan is only an untrusted candidate. The install script computes its
SHA-256 fingerprint and requires an exact match with the exported lab.yml
fingerprint before writing `control\known_hosts`. If it differs, stop and
verify at the console; never replace the inventory pin to make it work.

After the Proxmox stage succeeds, run the reviewed installer locally:

```powershell
& .\platform\proxmox\scripts\install-backup-pull-task.ps1 -NodeConfig D:\homelab-backups\backup-node.json -HostPublicKeyFile D:\homelab-backups\node-host-public.txt
Start-ScheduledTask -TaskName 'HomeLab Backup Pull'
Get-ScheduledTaskInfo -TaskName 'HomeLab Backup Pull'
```

The task is daily at 06:30 local time, `StartWhenAvailable=true`,
`WakeToRun=false`, least privilege and `InteractiveToken`. It catches a missed
start when Windows can run it, but requires the operator to be logged in.
It never changes power, firewall, networking or Windows features. It ignores
overlapping task starts; the script also holds an exclusive file lock.
The task uses `RemoteSigned` for its PowerShell process only, to run the reviewed
local script; it does not change any persisted Windows execution-policy setting.
The XML omits an encoding declaration so Windows can receive its Unicode
registration string. The installer stops on registration errors and retries
only when an existing pin exactly equals the already verified public key;
changed pins and existing tasks still stop for review.

The client selects only the newest finalized archive per VMID, checks existing
files before skipping them, downloads binary data into a unique same-directory
partial file, verifies size and SHA-256, re-lists the NAS once after the batch
to prove each source still matches, then atomically renames without overwrite.
Only two complete NAS manifest scans are needed for a batch. Failed partials are
retained for review. The log is `D:\homelab-backups\pull.log`.
Progress messages identify manifest hashing, downloads, local verification and
the final NAS recheck. An initial manifest hashes every finalized archive and
can take time; a running task or a partial file is not proof of a valid copy.
At less than 100 GB free, or if a download would cross that reserve, it stops
with a report and preserves everything.

## Acceptance and rollback

After the first run, require task result 0 and `SUCCESS` in the log. Record
the newest copied archive's name, size and SHA-256 from `Get-FileHash`; compare
with the server's `list` entry before and after the pull. Require identical
hash and size and `NAS_UNCHANGED=true`; server tests also preserve archive
inode, size, mtime and ctime. Do not infer completion from task registration
or from `Start-ScheduledTask` returning.

Rollback disables/removes **only this task** and removes **only this public
key's restricted entry** on the confirmed node, through a separately reviewed
stage. Keep the forced-command script until no key references it. Preserve
all D: files and every NAS archive, including partials and logs. A restore
from this second copy is the later Phase 4 exit gate; it is not yet proven.
